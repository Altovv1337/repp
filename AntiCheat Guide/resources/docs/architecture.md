# Архитектура обнаружения — подробности

Этот документ дополняет раздел README «Архитектура обнаружения» и описывает
концептуальный конвейер проверки честности игрового процесса.

## Этапы работы

1. **Инициализация.** При запуске игры клиентский агент проверяет целостность
   игровых файлов и загруженных модулей.
2. **Мониторинг.** Во время сессии агент периодически собирает телеметрию:
   параметры ввода, список активных процессов, показатели производительности.
3. **Локальный анализ.** Простые аномалии (например, нереалистичная скорость
   реакции) отфильтровываются уже на клиенте.
4. **Передача на сервер.** Подозрительные события и агрегированная телеметрия
   отправляются на сервер для более глубокого анализа.
5. **Серверная проверка.** Сервер сопоставляет данные с моделью нормального
   поведения игрока и статистикой по всей популяции игроков.
6. **Решение.** По результатам анализа система может выдать предупреждение,
   временную блокировку или направить случай на ручную модерацию.

## Почему проверка проходит в несколько уровней

Ни один отдельный метод не даёт стопроцентной точности:

- **Client-side** проверки быстрые, но их проще всего компрометировать.
- **Kernel-level** доступ повышает видимость системы, но вызывает вопросы
  приватности и требует доверия пользователя.
- **Server-side** анализ сложнее обойти, но требует накопления данных во
  времени, поэтому не может сработать мгновенно.
- **ML/эвристика** хорошо ловит новые, ранее неизвестные схемы читерства, но
  чувствительна к ложным срабатываниям.

Именно поэтому современные решения комбинируют несколько уровней защиты.
